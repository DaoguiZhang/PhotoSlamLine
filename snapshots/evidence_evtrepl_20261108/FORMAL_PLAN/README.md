### 1.1 L_core 的配置就是封存的 `off_cfg`（重要复用事实）

`cells.csv` 的 `off_cfg` 列指向 `PSL-fullmap-exp-v1/configs/off/formal/*.off.yaml`，
与基准 gauss cfg 的差异**恰好只有三行**：

```
Optimization.weight_line_coherence: 0.001 -> 0.0
Optimization.weight_line_shape_ecc:  0.002 -> 0.0
Optimization.weight_line_shape_ori:  0.005 -> 0.0
```

这与本轮范围修正后的 `L_core` 定义**完全一致**，也与 `PSL-evtrepl/cfg_v2/*.nostruct.yaml`
在这三个键上完全相同。因此 L_core 的 Gaussian 配置**不需要新发明**：它就是封存协议里已有的 OFF 配置，
只是现在它从"消融项"变成"最终配置"，并由 `[LossCfg]/[LossAudit]` 证明了它真的不参与优化。

### 1.2 旧 300 项 L0 结果不能继承

`PSL-fullmap-lock-v1` 的 300 次历史实验用的是 `libgaussian_mapper.so 98cc87928caa5928…`，
而本轮冻结版本是 `538f4629…`。按"版本和协议匹配才复用"的约定，
**这 300 条历史数字不能直接当作本计划的 L_core 结果**，只能作为历史对照；
本计划的 150 个 L_core 项必须在新版本上重跑。（74/226 那一分类只说明"改动不会让旧结论失效"，
不等于"旧数字可用于新版本"。）

## 2. 复用范围的重新审查（74 / 226 不能自动继承）

此前给出的"受影响 74 / 证明未受影响 226"只对**当时分析过的那几条代码路径**成立：
回环路径、GBA 写回、合并、非单位尺度、线高斯更新路径。本轮新增/修改的内容里：

| 本轮改动 | 是否影响已封存结果的可复用性 |
|---|---|
| `System::Shutdown()` 等待有界 + 诊断 | **不影响**：只在关机路径，`mbShutDown` 之后执行，任何跟踪/建图/优化器状态都已冻结 |
| `runReplay()` 的 try/catch、`reportExitState()` | **不影响**：只在重放结束/失败路径 |
| 例程退出码 | **不影响**：进程退出时返回值 |
| 事件审计 `evtAuditKfInto()` | **谨慎**：它在生产消费点**读取**张量并做 CPU 拷贝，不写模型；但会改变时序与显存压力，**正式运行必须关闭**（默认关，需显式 `PHOTO_SLAM_EVT_AUDIT=1` 才生效） |
| `PHOTO_SLAM_PRINT_EFF_PARAMS` | 只多一行日志，默认关 |
| 结构损失审计 + 跳过守卫 | **不影响**：权重全 0 时整块不执行（`[LossAudit] active_steps=0`）；权重非 0 时与改前逐字等价（仅多两次整数自增） |

因此：**没有一条改动能让旧的 74/226 分类失效**，但也**不能**据此声称"旧结果可用于新版本"——
版本号变了（`libgaussian_mapper.so` 从 `d82b9cca…` 到 `538f4629…`），按约定"版本和协议匹配才复用"，
正式对比必须在新版本上重跑，而不是继承旧数字。

## 3. 不满足的前置条件（准确描述，不擅自绕过）

### 3.1 `O_core` 与 `L_core` 的共同条件仍需人拍板

`cells.csv` 指向 `PSL-fullmap-exp-v1/bin/*`（带线前端 + 线高斯的 L 管线），
而 `O_core`（官方 + 公共修复）**没有线前端、没有 `GaussianModelLine`、没有 `weight_line_*`**。
把 `off_cfg` 套给 O_core 只是无害（那三个键在 O_core 里根本不存在），
**并不能**把"线采样点作为高斯种子"这条初始化路径也关掉。所以"O_core 用同一份 off_cfg"
与 "L_core 用同一份 off_cfg" 不是同一个实验条件。

范围修正又明确要求"不新增 L 点-only 分支"，因此不能靠新增开关解决。剩下的可行形式：

* **(a) 接受差异、按"方法层"比较**：两个方法各自用自己的完整管线，共享数据集/标定/预算/
  步调节奏/精修/评测协议，并在报告里**显式声明**“两者线初始化路径不同”，
  结论只声称“在相同输入与预算下最终指标差异”，不声称“线高斯本身是唯一原因”。
* **(b) 在报告外再补一个"线初始化关闭"的 L 旁路**（需新开关，已被本次范围修正排除）。

在选定前，正式的“O_core vs L_core”数字会混入线初始化差异，因此不启动。

### 3.2 墙钟与磁盘预算不足

30 格 × 5 次 × 2 方法 = **300 次整系统运行**。实测本机 office0（1200 帧）≈ 320 s、
desk_3（1144 帧）≈ 233 s；协议每格 2000 帧，单次保守按 240–420 s 计 →
**300 × ≈ 300 s ≈ 25 小时**连续串行。本轮会话无法在保证质量的前提下完成，
且"设个小额度后遗留未验收任务"被明确禁止。
另：`overlay` 已 99% 使用（~22 GB 可用），300 次整系统产物需先确认存放位置。

### 3.3 已关闭的旧前置（不再是阻塞项）

* 门禁 5（事件对象集合一致性）= NOT_VERIFIED：**不再阻塞**，因为 N 已显式设为 0、
  不进正式版；该项作为"能力边界"保留在 `GATES.md`，不作为正式计划的前置。
* "是否包含 L_core-Full"：已由本轮范围修正定为**不包含**。

## 4. 一旦前置条件满足，直接可用的东西

`schedule_formal.sh`（同目录）：

* **单实例**：`flock` 锁文件，第二个实例直接退出；
* **可恢复**：每格完成后写 `done/<cell>__<group>__r<k>.ok`（含 PID、退出码、墙钟、
  产物哈希），重跑时跳过已完成；只续跑缺失项；
* **串行**：一次只跑一个进程，避免 GPU 争用污染耗时；
* **不重试**：低画质、初始化失败、跟踪失败都**不重跑**，原样记录
  （`status=LOW_PSNR|INIT_FAIL|TRACK_FAIL|OK`）；
* **真实 PID / 进度**：`progress.jsonl` 每行一个事件（start/finish，含 pid、rc、秒数）；
* **不覆盖旧结果**：输出目录含版本哈希，已存在且非空则拒绝；
* 版本信息写进每个产物目录的 `PROVENANCE.txt`（二进制 sha256、cfg sha256、开关取值）。
